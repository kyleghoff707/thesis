# Thes1s Pipeline Migration to Claude Managed Agents

## What you're doing

Migrating the Thes1s AI investment research pipeline to Claude Managed Agents (Anthropic's hosted agent service). This replaces the failed Cloudflare Workers/Durable Objects approach AND the original browser-side pipeline.

## Why — the hard-won lesson

### The browser pipeline (v1) — worked but fragile
The pipeline originally ran in-browser. It worked. It had live UX (timer, phase indicators, section-by-section progress). But tab close killed $10+ reports, errors were silently swallowed, and there was no server-side billing enforcement.

### The Cloudflare Workers migration (v2) — failed
In April 2026, we attempted a "Workers-only" server-side migration. The eng review chose "boring by default" over Managed Agents because the API was 2 days old. This was the wrong call. Here's what happened:

1. **ctx.waitUntil() dies at 30-60s** — Verified experimentally. Can't run any Claude API call (30-120s each) in a background Worker task. Required switching to Durable Objects.

2. **Durable Objects have the SAME ctx.waitUntil() limit** — Not documented. Discovered after deploying. The DO's `fetch()` handler must `await` the full pipeline (keeping the DO alive for 5-15 minutes). The Worker route must fire-and-forget the `stub.fetch()` call.

3. **Import chain contamination** — `edgarFinancials.js` → `cache.js` → `cacheStore.js` → `idb` (browser-only). Also `apiBase.js` uses `import.meta.env` (Vite-only). Required esbuild `[alias]` and `[define]` shims in `wrangler.toml` to resolve. Works but fragile.

4. **Agent dispatch duplicated** — Couldn't import `aiResearch.js` or `pipelineManager.js` directly (Vite `?raw` contamination in `knowledgeBundle.js`). Had to reimplement 200+ lines of prompt assembly, retry logic, and JSON extraction in `agentDispatch.js`. DRY violation. Two sources of truth for prompt logic.

5. **Wave orchestration reimplemented** — `PipelineRunner.js` reimplements the wave dispatch from `pipelineManager.js` instead of reusing it. Another DRY violation, another source of truth.

6. **Entire generation UX lost** — The browser pipeline had `GenerationStatusPanel` with timer, phase indicators, section-by-section status. The server-side pipeline writes progress to D1 in a completely different shape. The existing UI components can't read it. Wiring the progress adapter was deferred and never completed.

7. **4 deploy attempts, pipeline still broken** — ctx.waitUntil killed pipelines twice (once in Workers, once in DOs). The One Pager dispatch for COST never completed. Zero successful pipeline runs on the server.

**Total cost: ~1800 lines of new code, 5 commits, 0 working pipeline runs.**

The conclusion: **this agent team is too complex for hardcoded orchestration.** 12 agents, 3 stages, wave dependencies, sequential debate, PSR pre-processing, checkpoint/resume — this needs a professional orchestration framework, not hand-rolled dispatch logic.

## The architecture (Pattern 1 — single coordinator with custom tools)

Use Pattern 1 from the migration analysis. This is production-stable today. DO NOT use multi-agent/callable_agents (research preview, not stable).

```
USER                  WORKER                    MANAGED AGENT           CLAUDE API
  │                     │                           │                      │
  ├─ POST /pipeline/run─►│                           │                      │
  │◄─ 202 {runId}───────┤                           │                      │
  │                     ├─ POST /v1/sessions ───────►│                      │
  │                     │◄─ {sessionId} ────────────┤                      │
  │                     ├─ POST events (user.message)►│                      │
  │                     │                           ├─ agent.custom_tool_use │
  │                     │◄─ get_data_packet ────────┤  (session pauses)     │
  │                     ├─ assembleDataPacketServer()│                      │
  │                     ├─ user.custom_tool_result──►│                      │
  │                     │                           ├─ run_agent ───────────►│
  │                     │◄─ agent.custom_tool_use ──┤                      │
  │                     ├─ dispatchAgent() ─────────┤                      │
  │                     │  (Messages API call) ─────┤──────────────────────►│
  │                     │◄─ response ───────────────┤◄─────────────────────┤
  │                     ├─ user.custom_tool_result──►│                      │
  │                     │   ... (repeat per agent)   │                      │
  │                     │                           ├─ save_report ─────────│
  │                     │◄─ agent.custom_tool_use ──┤                      │
  │                     ├─ save to D1 ──────────────┤                      │
  │                     ├─ user.custom_tool_result──►│                      │
  │                     │                           │                      │
  ├─ GET /pipeline/status►│                           │                      │
  │◄─ {progress} ───────┤ (reads D1 + session events)│                      │
```

The key insight: **the coordinator is a Managed Agent** running server-side. It decides when to dispatch analyst agents based on natural language instructions in its system prompt (wave logic described in English, not code). Each "analyst agent" is exposed as a **custom tool** — when the coordinator calls `run_agent(role, sections)`, your Worker dispatches the actual Claude Messages API call and returns the result.

This means:
- **Session durability** — Managed Agent sessions survive everything. Anthropic handles state.
- **No wall-clock limits** — Sessions run as long as needed.
- **Natural language orchestration** — Wave logic is a prompt, not code. Easy to change.
- **Event streaming** — Real-time progress via SSE from the session.
- **Automatic context management** — Anthropic handles compaction and caching.
- **The agent specs don't change** — Same prompts, same curriculum, same methodology.

## Custom tools to define

| Tool | Purpose | Executed by Worker |
|------|---------|-------------------|
| `get_data_packet(ticker)` | Assembles ~50KB DataPacket from D1/R2/SEC/Yahoo | `dataPacket.js` assembleDataPacketServer() — ALREADY WORKS |

| `save_progress(runId, wave, sections)` | Checkpoints progress to D1 pipeline_runs | D1 UPDATE (existing pattern) |

## Post-migration optimization (TODO after Managed Agents is working)

Once the pipeline is live on Managed Agents, these structural optimizations become possible with zero code changes to the Worker or custom tool handlers. They only require editing agent specs + the coordinator's system prompt.

### Stage-specific agents
Split agents that currently serve multiple stages into dedicated per-stage versions. For example, `business-analyst` becomes `business-analyst-onepager`, `business-analyst-pitchdeck`, `business-analyst-fullstory`. Each gets a prompt tailored to its specific stage output, eliminating the stage overlay system and reducing prompt size.

### Merge curriculum into agent prompts
Currently, curriculum files (pitch-deck-I.md, story-form-II.md, etc.) are shared across agents and appended at dispatch time. This wastes tokens because agents receive curriculum irrelevant to their role. Merging the relevant curriculum directly into each agent's prompt eliminates redundant context and reduces input tokens per call. The `build-curriculum.mjs` script and `CURRICULUM_MAP` become simpler (or unnecessary for merged agents).

### The workflow for structural changes
1. Edit agent specs locally (`agents/*/config.json`, `agents/*/prompt.md`)
2. Test with browser pipeline (free via Pro Max 20x plan)
3. Score output with eval framework, compare before/after
4. Update coordinator system prompt to reference new agent names/structure
5. `wrangler deploy` — build script regenerates bundle, coordinator uses new names
6. No Worker code changes. No custom tool handler changes. Just text.

This is the key advantage of Managed Agents over hardcoded orchestration. The coordinator's wave logic is natural language, not code. Changing agent structure means editing a prompt, not rewriting a dispatch engine.

### Observability + scoring framework (required for optimization)
You can't improve what you can't measure. Before optimizing agents, build:
1. **Run traces** — per-agent tokens/cost/latency, per-section verdicts/confidence. Managed Agents session events provide this in production. `contextBudget.js` provides it locally.
2. **Quality scoring** — methodology compliance, verdict consistency, ground truth comparison against user's own analyses (EW, SFM, MU, ODFL), citation verification.
3. **Regression gate** — automated check that prompt changes don't degrade output quality. Run before deploying agent changes.
