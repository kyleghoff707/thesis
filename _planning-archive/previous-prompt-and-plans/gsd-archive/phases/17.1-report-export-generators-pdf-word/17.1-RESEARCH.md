**Researched:** 2026-04-01
**Domain:** Python PDF/Word document generation from pipeline JSON output
**Confidence:** HIGH

## Summary

This phase refactors the existing hardcoded PDF generators into generic, ticker-agnostic export tools and adds Word document (.docx) generators for all three pipeline stages. The existing codebase has two PDF generators (`generate_one_pager_pdf.py` for CEG and `generate_pitch_deck_pdf.py` for SFM) plus a shared `pdf_template_toolkit.py` base class. Both generators need significant refactoring: the One Pager generator is entirely hardcoded to CEG with literal chart data, while the Pitch Deck generator accepts a ticker argument but reads from `pitch-deck.json` (which doesn't exist in the new pipeline -- the output is `pipeline-output.json`) and expects different section keys than the actual pipeline produces. No Full Story PDF generator exists at all.

The pipeline output across all three stages follows a consistent schema: sections array where each section has `{key, title, sectionNumber, status, confidence, verdict, verdictRationale, summary, data, narrative, citations, tables, charts, redFlags}`. The Full Story adds `debateOutputs` at the top level and checklist items in section `data`. The consistency of this schema creates an opportunity for a shared "section renderer" abstraction that both PDF and Word generators can use, reducing duplication dramatically.

**Primary recommendation:** Create new generic generators (don't refactor in-place) that read from the standardized pipeline output format. Extract a shared `report_data_reader.py` module that normalizes data access across all three stages. Build the Word generators using python-docx 1.2.0 (already installed) with the same section-rendering pattern as PDF but without chart rendering (tables and formatted text only).

### Pattern 1: Data Reader Abstraction
**What:** A single module that normalizes JSON access across all 3 pipeline output formats (one-pager.json, pipeline-output.json, full-story-api.json).
**When to use:** Every generator calls this instead of reading JSON directly.
**Why:** The three pipeline outputs have slightly different top-level structures (One Pager has `overallVerdict` + `sectionKeys` at top level; Pitch Deck and Full Story have these inside the `overall_verdict` section's `data`). The reader normalizes these differences.

```python
# report_data_reader.py

class ReportData:
    """Unified access to pipeline output data for any stage."""
    
    def __init__(self, ticker, stage):
        """
        stage: 'one-pager' | 'pitch-deck' | 'full-story'
        Loads the appropriate JSON files from .thes1s/reports/{ticker}/
        """
        self.ticker = ticker
        self.stage = stage
        self.report = self._load_report()
        self.data_packet = self._load_data_packet()
        self.sections = {s['key']: s for s in self.report.get('sections', [])}
    
    def _load_report(self):
        """Load the stage-specific JSON file."""
        filenames = {
            'one-pager': 'one-pager.json',
            'pitch-deck': 'pipeline-output.json',
            'full-story': 'full-story-api.json',
        }
        # ...
    
    def get_company_name(self):
        """From data-packet or report top-level."""
        return (self.report.get('companyName') or 
                self.data_packet.get('companyInfo', {}).get('name', self.ticker))
    
    def get_overall_verdict(self):
        """Normalize: OP has it at top level, PD/FS have it in overall_verdict section data."""
        if 'overallVerdict' in self.report:
            return self.report['overallVerdict']
        ov = self.sections.get('overall_verdict', {})
        return ov.get('data', {}).get('overallVerdict', 'N/A')
    
    def get_section_keys(self):
        """Ordered list of section keys for this stage."""
        if 'sectionKeys' in self.report:
            return self.report['sectionKeys']
        return [s['key'] for s in self.report.get('sections', [])]
    
    def get_financial_years(self, n=5):
        """Get the last N fiscal years from the data packet."""
        years = self.data_packet.get('financials', {}).get('years', [])
        return years[-n:]
    
    def get_debate_outputs(self):
        """Full Story only -- returns debateOutputs dict."""
        return self.report.get('debateOutputs', {})
```

### Pattern 2: Section Renderer Functions (shared between PDF and Word)
**What:** Pure functions that extract rendering data from sections, called by both PDF and Word generators.
**When to use:** Rendering any section's narrative, tables, citations, red flags, or verdicts.

```python
# section_renderers.py

def get_narrative(section):
    """Get best available text for a section."""
    narr = section.get('narrative', '')
    if narr and len(narr) > 100 and not narr.startswith('See full'):
        return narr
    parts = []
    vr = section.get('verdictRationale', '')
    if vr:
        parts.append(vr)
    sm = section.get('summary', '')
    if sm:
        parts.append(sm)
    return '\n\n'.join(parts)

def get_tables(section):
    """Get tables, filtering out non-dict entries (polymorphism guard)."""
    return [t for t in section.get('tables', []) if isinstance(t, dict) and t.get('headers')]

def get_red_flags(section):
    """Normalize red flags to strings."""
    flags = []
    for rf in section.get('redFlags', []):
        if isinstance(rf, str):
            flags.append(rf)
        elif isinstance(rf, dict):
            flags.append(rf.get('flag', rf.get('detail', str(rf))))
    return flags

def get_citations(section):
    """Normalize citations to dicts with {ref, text, source}."""
    cites = []
    for c in section.get('citations', []):
        if isinstance(c, dict):
            cites.append({
                'ref': c.get('ref', c.get('claim', c.get('field', ''))),
                'text': str(c.get('text', c.get('value', ''))),
                'source': c.get('source', c.get('url', 'DataPacket')),
            })
        elif isinstance(c, str):
            cites.append({'ref': c, 'text': '', 'source': ''})
    return cites

def get_checklist_items(section):
    """Full Story checklist sections: extract scored items."""
    data = section.get('data', {})
    if not isinstance(data, dict):
        return []
    return data.get('items', data.get('checklistItems', []))
```

### Anti-Patterns to Avoid
- **Hardcoding chart data:** The CEG One Pager generator has literal values like `['-160e6, 1623e6, 3749e6, 2319e6']` -- the new generators must pull all data from JSON or DataPacket.
- **Section key mismatch:** The existing PD generator uses `simple_predictable` but pipeline output uses `simple_and_predictable`. Use the actual keys from the pipeline output.
- **Expecting top-level fields:** The existing PD generator reads `rpt['overallVerdict']` and `rpt.get('synthesisNarrative')` and `rpt.get('fgrDerivation')` at top level -- none of these exist in the current pipeline output format. They're inside section data.
- **Copy-pasting the Thes1s class:** Don't create yet another copy of OnePagerPDF/PitchDeckPDF -- extract once, subclass thrice.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Word tables with cell shading | Manual XML construction | python-docx Table + `parse_xml` for shading | Cell shading requires one line of XML per cell, well-documented pattern |
| PDF charts from scratch | New chart primitives | Existing ReportPDF/Thes1s chart methods | draw_bar_chart, draw_comparison_bar_chart, draw_verdict_scorecard, draw_price_range_chart already work |
| JSON normalization per generator | Per-file JSON parsing | ReportData class | Three different JSON formats need one normalization layer |

**Key insight:** The existing PDF toolkit (`pdf_template_toolkit.py`) has all the chart/table/text primitives needed. The problem is entirely in the data access layer (hardcoded tickers, wrong filenames, wrong section keys) and missing generators (Full Story PDF, all Word docs).

## Common Pitfalls

### Pitfall 1: Section Key Mismatch Between Generator and Pipeline
**What goes wrong:** The existing PD generator expects section keys like `simple_predictable`, `barriers_moats`, `pest`, `valuation` but the pipeline output uses `simple_and_predictable`, `barriers_and_moats`, `pest_risks`, `valuation_summary`.
**Why it happens:** The generators were built before the pipeline API was finalized; section keys diverged.
**How to avoid:** Use the section keys exactly as they appear in the pipeline output. The ReportData class should provide iteration over actual sections, not hardcoded key lists.
**Warning signs:** KeyError when accessing `sections[key]` or missing sections in the output PDF.

### Pitfall 2: Missing Top-Level Fields in Pipeline Output
**What goes wrong:** The existing PD generator reads `rpt['overallVerdict']`, `rpt.get('synthesisNarrative')`, and `rpt.get('fgrDerivation')` from the top level. These don't exist in the current pipeline output format (MNST).
**Why it happens:** The old SFM pitch-deck.json was a different format (CC pipeline era) with these fields at top level. The new API pipeline puts them inside section data.
**How to avoid:** The `overall_verdict` section's `data` dict contains `overallVerdict`, `keyStrengths`, `keyConcerns`, `nextSteps`. The `valuation_summary` section's `data` contains `fgrDerivation`, buy price ranges, etc. Always access through section data, not top-level.
**Warning signs:** "N/A" or empty strings on the title page where verdict should appear.

### Pitfall 3: One Pager Data vs PD/FS Data Asymmetry
**What goes wrong:** One Pager sections have `data: "{}"` (empty string of JSON), no tables, no charts. PD/FS sections have rich `data` dicts, multiple tables, and chart descriptors.
**Why it happens:** The One Pager uses a single-call generator (Phase 16.1) that produces flat sections with narrative-only output. PD/FS use multi-agent pipelines with structured data.
**How to avoid:** The One Pager PDF/Word should be primarily narrative-driven with charts pulled from DataPacket (the same pattern the CEG generator uses). PD/FS generators can render section tables directly from the JSON.
**Warning signs:** Empty pages in One Pager if you try to render `section.data` or `section.tables`.

### Pitfall 4: Chart Data in Pipeline Output is Descriptive, Not Numeric
**What goes wrong:** Trying to use `section.charts` as data arrays for drawing charts.
**Why it happens:** The `charts` field in pipeline output contains descriptive objects like `{type: "bar_with_line", title: "...", dataSource: "dataPacket.fcf.yearly"}` -- they tell you what to chart, not the numbers.
**How to avoid:** For PDF charts, pull actual numeric data from `data-packet.json` (via `ReportData.data_packet`), just like the existing generators do. For Word docs, skip charts entirely and use tables instead.
**Warning signs:** TypeError when passing chart descriptors to draw_bar_chart().

### Pitfall 5: Agent Output Polymorphism
**What goes wrong:** Assuming tables are always dicts, citations always dicts, red flags always strings.
**Why it happens:** Different agent runs may produce slightly different output shapes. Tables can sometimes be strings. Citations can be strings or ints. Red flags can be dicts with `{flag, detail}` keys.
**How to avoid:** Every rendering function must type-check its input. The `section_renderers.py` helper functions above include these guards. Always use `isinstance()` checks.
**Warning signs:** `AttributeError: 'str' object has no attribute 'keys'` during rendering.

### Pitfall 6: Word Documents Without Explicit Font Setting
**What goes wrong:** Word docs use Calibri by default (the python-docx default template), which doesn't match the Thes1s brand (Arial/system font).
**Why it happens:** python-docx uses a built-in default template.
**How to avoid:** Explicitly set the Normal style font to Arial and configure heading styles to match Thes1s branding (teal headings, slate body text).
**Warning signs:** Generated Word docs look like generic business letters instead of branded reports.

import json, os

def load_report_data(ticker, stage):
    """
    stage: 'one-pager' | 'pitch-deck' | 'full-story'

    return report, dp, sections

### Rendering a Section in PDF (generic pattern)
```python
def render_section_pdf(pdf, section, section_num):
    """Generic section renderer for any stage's section."""
    title = f"{section_num}. {section.get('title', section['key'])}"
    pdf.add_smart_section_header(title)
    
    # Narrative
    narr = get_narrative(section)
    if narr:
        _render_narrative_pdf(pdf, narr)
    
    # Tables
    for table in get_tables(section):
        title = table.get('title', '')
        if title:
            pdf.add_section_header(title, level=2)
        pdf.add_table(table['headers'], table.get('rows', []))
    
    # Red flags
    flags = get_red_flags(section)
    if flags:
        pdf.add_section_header('Red Flags', level=3)
        for f in flags:
            pdf.add_bullet(f)
    
    # Citations (inline, not as a separate page)
    cites = get_citations(section)
    if cites:
        pdf.add_section_header(f'Citations', level=3)
        for i, c in enumerate(cites, 1):
            line = f"[{i}] {c['ref']}"
            if c['text'] and len(c['text']) < 120:
                line += f" = {c['text']}"
            if c['source']:
                line += f"  ({c['source']})"
            pdf.add_bullet(line, indent=2)
```

def render_debate_pdf(pdf, debate_outputs):
    """Render the 4-step adversarial debate."""
    pdf.add_section_header('Adversarial Debate: Inversion & Rebuttal', level=1)
    
    # Bull Thesis
    bull = debate_outputs.get('bull', {}).get('content', {})
    if bull:

    # Bear Inversion
    bear = debate_outputs.get('bear', {}).get('content', {})
    if bear:
        pdf.add_section_header('Bear Inversion', level=2)
        bear_case = bear.get('overallBearCase', '')
        if bear_case:
            pdf.add_body_text(bear_case)
        for inv in bear.get('inversions', []):
            severity = inv.get('severity', 'MEDIUM')
            pdf.add_bullet(f"[{severity}] {inv.get('counterArgument', '')[:200]}")
    
    # Bull Rebuttal
    rebuttal = debate_outputs.get('bull_rebuttal', {}).get('content', {})
    if rebuttal:
        pdf.add_section_header('Bull Rebuttal', level=2)
        for reb in rebuttal.get('rebuttals', []):
            strength = reb.get('rebuttalStrength', 'N/A')
            pdf.add_bullet(f"[{strength}] {reb.get('rebuttal', '')[:200]}")
    
    # Judge Verdict
    judge = debate_outputs.get('judge', {}).get('content', {})
    if judge:
        pdf.add_section_header('Judge Verdict', level=2)

            pdf.add_body_text(f"Direction: {verdict.get('direction', 'N/A')}")
            pdf.add_body_text(f"Unresolved Risks: {verdict.get('unresolvedCount', 0)}")
            pdf.add_body_text(verdict.get('summary', ''))
        
        # Exchange table
        exchanges = judge.get('exchanges', [])

            rows = [[
                e.get('topic', ''),
                e.get('bullStrength', ''),

                e.get('verdict', ''),
            ] for e in exchanges]

### Word Document Table with Thes1s Styling
```python
from docx.oxml.ns import nsdecls
from docx.oxml import parse_xml
from docx.shared import Pt, RGBColor

def add_styled_table(doc, headers, rows):
    """Add a Thes1s-branded table to a Word document."""
    table = doc.add_table(rows=1 + len(rows), cols=len(headers))
    table.style = 'Table Grid'
    
    # Header row
    for i, header in enumerate(headers):
        cell = table.rows[0].cells[i]
        cell.text = header
        # Teal background
        shading = parse_xml(f'<w:shd {nsdecls("w")} w:fill="0F766E"/>')
        cell._tc.get_or_add_tcPr().append(shading)
        run = cell.paragraphs[0].runs[0]
        run.font.bold = True
        run.font.size = Pt(9)
        run.font.color.rgb = RGBColor(255, 255, 255)
    
    # Data rows
    for row_idx, row_data in enumerate(rows):
        for col_idx, cell_text in enumerate(row_data):
            cell = table.rows[row_idx + 1].cells[col_idx]
            cell.text = str(cell_text)
            run = cell.paragraphs[0].runs[0] if cell.paragraphs[0].runs else cell.paragraphs[0].add_run(str(cell_text))
            run.font.size = Pt(9)
            # Alternating row shading
            if row_idx % 2 == 0:
                shading = parse_xml(f'<w:shd {nsdecls("w")} w:fill="F0FDFA"/>')
                cell._tc.get_or_add_tcPr().append(shading)
```

## Critical Data Schema Findings

The existing generators and the actual pipeline output use different section keys:

| Existing PD Generator Key | Actual Pipeline Output Key | Notes |
|---|---|---|
| `simple_predictable` | `simple_and_predictable` | Underscores vs full name |
| `barriers_moats` | `barriers_and_moats` | Same pattern |
| `roe_roic_debt` | (removed) | This section doesn't exist in current pipeline |
| `pest` | `pest_risks` | Suffix added |
| `valuation` | `valuation_summary` | Suffix added |

| N/A (`rpt.get('fgrDerivation')` top-level) | `sections['valuation_summary'].data.fgrDerivation` | Moved inside section data |
| N/A (`rpt.get('sectionKeys')`) | Not available as top-level field for PD/FS | Derive from sections array |

## Design Decisions (Claude's Discretion)

### Decision 1: Create New Generic Generators (Don't Refactor In-Place)
**Recommendation:** Write new files. Keep old ones as reference until validation confirms the new ones work.
**Rationale:** The existing generators have ~80% hardcoded data (CEG literally, SFM via wrong section keys + wrong filenames + wrong top-level fields). Refactoring in-place would be more work than rewriting, and the old files serve as reference for the visual design.

### Decision 2: Use python-docx (Confirmed)
**Rationale:** Already installed (v1.2.0), de facto standard, supports tables with cell shading, heading styles, paragraph formatting, page breaks. No alternative needed.

### Decision 3: Skip Charts in Word Docs
**Recommendation:** Word docs are text + tables only. No chart images.
**Rationale:** Embedding fpdf2 charts as images in Word requires: (1) rendering to a temp PNG (fpdf2 doesn't natively export individual chart images), (2) inserting the PNG into docx. This adds significant complexity for marginal value. The Word docs are a "portable text format" -- users who want charts use the PDF.
**Alternative considered:** matplotlib chart images. Rejected because it adds a heavy dependency and the PDF already serves the "visual" use case.

### Decision 4: Shared Section Renderer Layer
**Recommendation:** Extract `section_renderers.py` with pure functions that return structured data (not format-specific). PDF and Word generators each call these functions and render in their format.
**Rationale:** Narrative extraction, table normalization, citation normalization, red flag normalization, and checklist extraction are identical regardless of output format. The ~10 helper functions save duplicating logic across 6 generators.

### Decision 5: One Pager Charts from DataPacket
**Recommendation:** The One Pager PDF should pull financial chart data from `data-packet.json`, not from section data (which is empty `{}`). Render key metrics gauges, verdict scorecard, and a few financial bar charts. Word version gets tables instead.
**Rationale:** This matches what the existing CEG generator does (it pulls chart data from CEG's data packet). The difference is it must be generic -- pull the most recent 3-5 years, auto-detect which metrics are available.

## Open Questions

1. **SFM Pipeline Output Compatibility**
   - What we know: SFM's `pipeline-output.json` has different section keys than MNST (it includes reader sections like `annual-reader-SFM`). It was generated by the older CC pipeline.
   - What's unclear: Should the new generators support the old CC pipeline format, or only the new API pipeline format?
   - Recommendation: Support both by filtering out reader sections (skip any section with `reader` in the key) and mapping old section keys to new ones. The ReportData class handles this.

2. **Chart Selection for Generic One Pager**
   - What we know: The CEG generator hand-picked which charts to show (net income trajectory, operating cash flow, EBITDA, ROE vs ROIC, etc.). A generic generator can't hand-pick.
   - What's unclear: Which charts work universally across all tickers?
   - Recommendation: Show a standard set: (1) Revenue trajectory, (2) EPS trajectory, (3) Rule One gauges from scores, (4) Verdict scorecard, (5) Buy price ranges if available in DataPacket. Skip company-specific narratives that the CEG generator had.

3. **Full Story PDF Page Count**
   - What we know: Full Story has 6 sections with extensive evidence text (7K-14K chars per section) plus a 4-step debate with 7 exchanges each. Could produce 50+ page PDFs.
   - What's unclear: Is that acceptable, or should we truncate?
   - Recommendation: Render everything. These are hedge-fund-quality research reports -- completeness is the point. The narrative and evidence text IS the product.
