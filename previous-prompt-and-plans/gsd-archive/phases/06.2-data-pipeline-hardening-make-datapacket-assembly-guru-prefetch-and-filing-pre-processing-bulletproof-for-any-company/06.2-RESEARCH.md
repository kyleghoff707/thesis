# Phase 06.2: Data Pipeline Hardening - Research

**Researched:** 2026-03-26
**Domain:** DataPacket assembly, SEC filing extraction, guru prefetch, pipeline reliability
**Confidence:** HIGH

## Summary

Phase 6.2 hardens three specific subsystems in the pitch deck generation pipeline: DataPacket assembly (25-field data collection with fallback chains), guru prefetch (CUSIP-to-ticker resolution), and filing pre-processing (form-aware section extraction for 10-K and 10-Q). All three subsystems exist and mostly work, but have documented failure modes discovered during real COST and SFM generation runs. This phase also adds a data quality checkpoint that gates agent dispatch.

The research examined every source file to be modified, verified the root causes documented in CONTEXT.md, confirmed the 10-Q item numbering mismatch, traced the guru CUSIP resolution flow, measured actual DataPacket population rates, and identified the exact retry/fallback patterns needed. The existing codebase already has the building blocks (nodeYahoo.js, nodeFinviz.js, resolveTickersForHoldings, cache.js) -- this phase wires them together with reliability patterns.

**Primary recommendation:** Fix the three known bugs (10-Q SECTION_MAP, guru ticker resolution, analystEstimates fallback), add retry-with-backoff to dataExport.js, optimize parallelization, and insert a checkpoint step in the SKILL.md pipeline between data assembly and agent dispatch.

### Pattern 1: Fallback Chain with Retry (D-08, D-09)
**What:** Try primary source, retry once on timeout/failure, fall back to alternative source, then mark unavailable.
**When to use:** Any DataPacket field that has multiple possible data sources.
**Example:**
```javascript
// Pattern: retry-then-fallback for any engine call
async function fetchWithFallback(ticker, label, errors) {
  // Attempt 1: primary source
  try {
    return await withTimeout(primaryFetch(ticker), 15000);
  } catch (err1) {
    // Attempt 2: retry primary after backoff
    await sleep(5000);
    try {
      return await withTimeout(primaryFetch(ticker), 15000);
    } catch (err2) {
      // Attempt 3: fallback source
      try {
        return await fallbackFetch(ticker);
      } catch (err3) {
        errors.push(`${label}: primary failed (${err1.message}), fallback failed (${err3.message})`);
        return null;
      }
    }
  }
}
```

### Pattern 2: Form-Aware Section Extraction (D-05)
**What:** Separate SECTION_MAPs for 10-K and 10-Q, with form type parameter flowing through the extraction chain.
**When to use:** Any SEC filing section extraction.

10-K and 10-Q use different item numbers for the same content:

| Content | 10-K Item | 10-Q Item |
|---------|-----------|-----------|
| Financial Statements | Item 8 (Part II) | Item 1 (Part I) |
| MD&A | Item 7 (Part II) | Item 2 (Part I) |
| Risk Factors | Item 1A (Part I) | Item 1A (Part II) |
| Market Risk | Item 7A (Part II) | Item 3 (Part I) |
| Controls | Item 9A (Part II) | Item 4 (Part I) |

**Recommended approach: Separate SECTION_MAPs** (not dual-pattern regexes). Cleaner, easier to test, no risk of cross-contamination between form types.

```javascript
// Separate maps — cleaner than dual-pattern regexes

  'MD&A': /^(?:#{1,3}\s*)?Item\s*7[.:\s]\s*Management[''\u2019]?s?\s*Discussion/im,
  'Financial Statements': /^(?:#{1,3}\s*)?Item\s*8[.:\s]\s*Financial\s*Statements/im,
```

### Pattern 3: Data Quality Checkpoint (D-11)
**What:** A summary table printed between data assembly and agent dispatch that classifies fields as critical vs. non-critical and gates pipeline continuation.
**When to use:** After Step 2.5, before Step 3 in the SKILL.md pipeline.

```
Critical fields (block dispatch if missing):
  - companyInfo, financials, filings

Non-critical fields (warn but continue):
  - analystEstimates, transcriptAvailability, gurus, compensation, events

Filing quality (block if zero sections):
  - 10-K sections (need at least Business, Risk Factors, MD&A, Financial Statements per filing)
  - 10-Q sections (need at least MD&A, Financial Statements per filing)
```

### Anti-Patterns to Avoid
- **Modifying engine source files for Node.js compatibility:** Always extend nodeAdapter.js instead. Zero engine files were modified in Phase 6.1 -- maintain this pattern.
- **Inline pipeline code in SKILL.md:** Phase 6.1 proved that standalone scripts (prefetch-gurus.js, preprocess-filings.js, assemble-data.js) are more reliable than inline code in SKILL.md. The checkpoint should also be a script.
- **Swallowing errors silently:** The `return null` pattern is correct, but errors MUST be pushed to the errors array so they appear in the checkpoint table. Caller checks for null.

## Common Pitfalls

### Pitfall 1: 10-Q Item 1 vs 10-K Item 1 Collision
**What goes wrong:** If using a single SECTION_MAP, `Item 1` matches "Business" (10-K) when it should match "Financial Statements" (10-Q), or vice versa.
**Why it happens:** 10-K Item 1 = Business; 10-Q Item 1 = Financial Statements. Same item number, different content.
**How to avoid:** Separate SECTION_MAPs. Never use a single map for both form types.
**Warning signs:** 10-Q extraction returns "Business" section (should not exist in 10-Q).
**Verified:** SFM 10-Q-2025.json currently extracts only 1 section (Risk Factors) out of expected 3, confirming the root cause.

### Pitfall 2: Guru Holdings Without Ticker Resolution
**What goes wrong:** `findGurusOwning(portfolios, ticker)` searches by `h.ticker`, but 13F data only has CUSIPs. Returns 0 matches even when gurus hold the stock.
**Why it happens:** `fetchAllGuruHoldings()` returns raw SEC 13F data with CUSIP identifiers. The self-heal step (`resolveTickersForHoldings`) runs in `loadCachedPortfolios()` but NOT in `fetchAllGuruHoldings()`.
**How to avoid:** After calling `fetchAllGuruHoldings()` in the prefetch script, iterate portfolios and call `resolveTickersForHoldings()` on each portfolio's holdings.
**Warning signs:** Guru pre-fetch reports "0 guru(s) hold TICKER" despite well-known large-cap stocks.
**Verified:** Current `prefetch-gurus.js` (lines 32-38) calls `findGurusOwning(portfolios, ticker)` directly on unresolved portfolios.

### Pitfall 3: Yahoo Finance Timeout on analystEstimates
**What goes wrong:** `fetchAnalystEstimates()` in Node.js goes through the nodeAdapter fetch interceptor which calls `yahooSummary()` with a 30s timeout. Intermittent timeouts cause the field to be null.
**Why it happens:** Yahoo Finance's v10 quoteSummary endpoint is slow and sometimes rate-limits. The current code has no retry -- one failure = null field.
**How to avoid:** Add retry-with-backoff in dataExport.js's safeCall wrapper, plus a Finviz fallback for the growth rate estimate (the most critical data from analystEstimates).
**Warning signs:** DataPacket reports analystEstimates: null in the errors array.
**Verified:** SFM DataPacket (current state) has analystEstimates: null. Session handoff notes "Yahoo timeout on analystEstimates (known intermittent issue, 30s timeout)".

### Pitfall 4: Filing Filename Collisions with Multiple 10-Qs Per Year
**What goes wrong:** `preprocess-filings.js` writes output as `{form}-{year}.json` (e.g., `10-Q-2024.json`). With 8 quarters (D-04), a single year can have 3-4 10-Qs, causing overwrites.
**Why it happens:** Current naming uses filing date year only: `f.filingDate.slice(0, 4)`.
**How to avoid:** Use full date or quarter indicator in filename: `10-Q-2024-Q3.json` or `10-Q-2024-10-30.json`.
**Warning signs:** Expected 8 10-Q files but only 2-3 exist in filings-md/.

### Pitfall 5: resolveTickersForHoldings Requires EDGAR Ticker Index
**What goes wrong:** `resolveTickersForHoldings()` calls `getTickerSearchIndex()` which fetches the EDGAR full-text search index (company_tickers.json). In Node.js, this requires the fetch interceptor to be active.
**Why it happens:** The ticker index is fetched from EDGAR via the proxy route `/api/efts/`. nodeAdapter's fetch interceptor resolves this to `https://efts.sec.gov/`.
**How to avoid:** Ensure nodeAdapter.js is imported before calling resolveTickersForHoldings. The prefetch script already does `import '../src/engines/nodeAdapter.js'` at line 9.
**Warning signs:** resolveTickersForHoldings silently returns holdings unchanged (line 1049: `return holdings` on catch).

### Fix Pattern: analystEstimates Fallback Chain
```javascript
// FIX: Primary (Yahoo) → retry → fallback (Finviz) → null
async function fetchAnalystWithFallback(ticker, errors) {
  // Primary: Yahoo Finance via analystEstimates.js
  try {
    const result = await fetchAnalystEstimates(ticker);
    if (result) return result;
  } catch (e) { /* first attempt failed */ }

  // Retry after 5s backoff
  await new Promise(r => setTimeout(r, 5000));
  try {
    const result = await fetchAnalystEstimates(ticker);
    if (result) return result;
  } catch (e) { /* retry failed */ }

  // Fallback: Finviz scraping for growth estimates
  try {
    const finviz = await fetchFinvizData(ticker);
    if (finviz?.epsNext5Y != null) {
      return {
        growthRate: finviz.epsNext5Y,
        priceTargets: finviz.targetPrice ? { mean: finviz.targetPrice } : null,
        recommendation: finviz.recommendation ? { score: finviz.recommendation } : null,
        _source: 'finviz-fallback',
        _fetchedAt: Date.now(),
      };
    }
  } catch (e) {
    errors.push(`analystEstimates: Yahoo and Finviz both failed`);
  }
  return null;
}
```

### DataPacket Parallelization Analysis (D-10)

Current pipeline stages in dataExport.js:
```
Step 1 (sequential): fetchEdgarStatements + fetchCompanyInfo  (~10-15s)
Step 2 (parallel):   5 compute functions                      (~50ms, CPU-bound)
Step 3 (parallel):   9 external fetches                       (~15-30s)
Step 4 (sequential): peerMetrics + batchQuotes                (~5-10s, depends on Step 3 peers)
Step 5 (sequential): 3 composite scores                       (~10ms, CPU-bound)
```

**Optimization opportunities:**
1. Steps 1a (EDGAR statements) and 1b (companyInfo) can run in parallel with each other -- companyInfo only needs ticker, not statements.
2. Step 3 already uses Promise.allSettled (good).
3. Yahoo enrichment (lines 149-175) runs sequentially after Step 3 -- could overlap with Step 4 peer calculations.
4. `fetchEdgarStatements` is the single slowest call (~10-15s, multiple EDGAR API hits) -- no shortcut here, but everything else can overlap.

**Realistic time improvement:** Current 30-60s -> target 20-40s. EDGAR is the bottleneck; parallelizing Steps 1a/1b and overlapping Yahoo enrichment with peer calculations saves 5-15s.

## Open Questions

   - What we know: Finviz sometimes returns 403 for automated requests. nodeFinviz.js sends browser-like User-Agent headers.
   - What's unclear: How reliably does Finviz work as a fallback? May need a retry delay.
   - Recommendation: Try Finviz fallback with a 2s delay. If 403, log and move on -- analystEstimates is non-critical.

2. **Checkpoint script vs SKILL.md inline logic**
   - What we know: Phase 6.1 established standalone scripts as the reliable pattern.
   - What's unclear: Should the checkpoint be a Node script that outputs JSON, or SKILL.md inline logic that reads files?
