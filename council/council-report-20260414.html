Council Verdict

Thes1s Backend Architecture — 2026-04-14 — 5 advisors, 5 peer reviews, 1 chairman

The Recommendation

Browser assembles DataPacket. Worker relays to Managed Agent. Filing content pre-computed in R2 via cron.

  1. Browser runs 58 engines, assembles DataPacket (already works for Toolbox)
  2. Browser POSTs DataPacket to Worker
  3. Worker pulls pre-computed filing content from R2, appends to message
  4. Worker creates Managed Agent session, sends everything as one message
  5. Worker polls for completion (already built)

No MCP. No dynamic queries. No progressive enrichment. One shot, one message, all the data.

The One Thing to Do First

Wire the browser to POST its already-assembled DataPacket to /api/pipeline/run instead of having the Worker re-assemble it. The DataPacket assembly already works in the browser (powers every Toolbox tab). The Worker endpoint already creates agent sessions. Plumbing change, not architecture change.

Where the Council Agrees High Confidence

  • Browser-side DataPacket assembly. All 5 advisors independently. The 58 engines work at 94.8% accuracy in the browser. Moving them to a 30s CPU-limited Worker was fighting the platform.
  • Filing content is a separate problem. Number crunching (fast, cacheable) must not be conflated with filing HTML-to-markdown (slow, CPU-heavy). Filings are immutable — pre-compute via cron into R2.
  • Do not build MCP yet. Premature complexity for <10 users. Managed Agents consume data at message time and cannot call back. Dynamic queries are moot until Anthropic ships tool-use callbacks.
  • The real bottleneck is callable_agents access. Three peer reviews flagged this. Time on data flow architecture is time not spent on prompts and methodology.

Where the Council Clashes Tension

  • Browser reliability. Expansionist: every browser is a free compute node, scales to 1,000. Contrarian: user closes laptop mid-run, pipeline breaks. Resolution: at current scale, non-issue. Browser's job finishes in seconds (assemble + POST). Agent session runs server-side.
  • Keep Worker assemble-data endpoint? Executor says keep for debugging. First Principles says Worker shouldn't be in assembly path at all. Resolution: keep as diagnostic, remove from production pipeline.

Blind Spots Caught Critical

  • Managed Agents session lifecycle. The agent gets ONE message with all data. No callbacks, no MCP, no progressive enrichment. DataPacket must be complete at send time.
  • Token budget is the real constraint. The DataPacket gets serialized into the agent message. There's a token limit. DataPacket design is really a compression and prioritization problem.
  • Retry and failure handling. Nobody addressed what happens when assembly fails or how polling handles partial data.

Full Advisor Responses

The Contrarian

The previous recommendation was wrong because they didn't do the math. 30s CPU, 128MB memory, 10-20MB bank 10-Ks — that's a physics problem, not a scaling problem.

Option C will silently kill you. 5,758 companies, stale cache, every engine fix requires recompute.

Option A's fatal assumption: browser must be available when agent needs data. User closes laptop → agent calls dead MCP.

The hard truth: Split "financial number crunching" (fast, cacheable) from "filing content extraction" (slow, must be async). Every option that treats these as one pipeline hits the same wall.

The First Principles Thinker

Wrong question. "How should data flow between browser, Worker, and agents?" assumes the Worker needs to be in the assembly path. It doesn't.

Engines produce DataPacket. Agent consumes it. That's it. The assumption "server-side is more professional" is cargo-culting. Browser is the compute engine. Worker is an authenticated proxy.

The Expansionist

Browser engines are the most undervalued asset. Option A scales to 1,000 users — every browser is a free compute node. Think bigger: real-time DataPackets, offline-first, progressive enrichment, user-customized packets.

Peer review consensus: these are future features, not current priorities. Focus on shipping.

The Outsider

The Worker version literally imports from the same frontend code with a fetch interceptor bolted on. You rebuilt what already worked, in a worse environment.

Filings are immutable — pre-compute via cron into R2. You already have 5 cron jobs. Do NOT build MCP yet. Handle dynamic needs in the next polling cycle.

The Executor

Monday morning: (1) Browser assembles DataPacket, (2) POSTs to new Worker endpoint, (3) Filing content via cron/browser to R2, (4) Keep assemble-data for debugging.

Option C is overkill. MCP is future. Get Pitch Deck working with static DataPackets first.
