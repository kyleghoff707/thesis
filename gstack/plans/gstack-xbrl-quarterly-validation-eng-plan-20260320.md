## Root Cause Analysis (Baseline)

### Primary Issue: Comparative Period Contamination

EDGAR's companyfacts JSON includes **comparative prior-year data** re-reported in current-year 10-Q filings. Both entries carry the same `fy`, `fp`, and `form` metadata — the only distinguishing feature is the `start`/`end` date range.

**Example (AAPL, fy=2024, fp=Q1, Revenue):**
```
Entry 1 (comparative): start=2022-09-25, end=2022-12-31, val=117,154M  ← FY2023 Q1 data
Entry 2 (current):     start=2023-10-01, end=2023-12-30, val=119,575M  ← FY2024 Q1 data
```

Both have `fy=2024, fp=Q1, form=10-Q`. The current `getQuarterlyYTD` function picks the **longest duration** entry. For Q1, both durations are ~90 days (tied), so it falls to tiebreakers. For Q2/Q3, the comparative YTD may have slightly different calendar durations, causing wrong picks.

**Impact:** Cascading errors through de-cumulation:
- Q1-Q3 individual quarters: de-cumulation partially cancels (both Q2_YTD and Q1_YTD from same wrong year → Q2 = Q2_YTD - Q1_YTD works)
- Q4: `FY_total - Q3_YTD` mixes current FY total with wrong Q3 YTD → incorrect

**Fix:** Change `getQuarterlyYTD` to pick the entry with the **latest `end` date** instead of longest duration. Current-period entries always have later end dates than comparative entries (e.g., Q3 YTD ending Jun 2024 vs Jun 2023).

### Secondary Issue: Balance Sheet Comparative Snapshots

For instant (balance sheet) data, `getQuarterlyInstant` already picks the latest `end` date, which should correctly select the current quarter-end snapshot over the prior FY-end comparative. This likely works correctly — need to confirm after B1 fix.

### Tertiary Issue: Same Tag Coverage Issues as Annual

Fields like `depreciation_amortization`, `net_change_in_cash`, `accrued_liabilities`, etc. have the same structural mismatches documented in the annual plan. The quarterly test amplifies these because each mismatch produces 16-19 failures instead of 5.

### B2: Fix Share Count / EPS De-cumulation ✅ DONE

**Status:** ✅ COMPLETE
**Result:** 88.4% → **91.7%** (+3.3pp, +1,712 matches)
**Annual regression check:** 91.0% unchanged ✅

**Root cause:** Share counts (basic/diluted WASO) are *weighted averages*, not cumulative totals. The engine was de-cumulating them like flow items (`Q2 = Q2_YTD - Q1_YTD`), which produces nonsense values (e.g., -56M instead of 16B for AAPL). EPS was then derived from these broken share counts, cascading the error.

**What changed:**
1. New `getQuarterlySinglePeriod` helper — picks the **shortest-duration** entry per quarter (single-quarter value, not YTD), with latest `end` date for current-period filtering
2. `extractQuarterlySection` now has a separate `unit === 'shares'` branch that:
   - Extracts Q1-Q3 single-quarter share counts directly
   - Derives Q4 from `4 * FY_weighted_avg - Q1 - Q2 - Q3`

**What worked:**
- Share count failures: 514 → 60 (88% reduction)
- EPS failures: ~470 → dropped off top 20 entirely
- BOOT hit 99.3%, AAPL hit 98.1%, ULTA hit 98.5%

### B3: Fix YTD Duration Tiebreaker ✅ DONE

**Status:** ✅ COMPLETE
**Result:** 91.7% → **92.4%** (+0.7pp, AMZN 67.3% → 78.2%)
**Annual regression check:** 91.0% unchanged ✅

**Root cause:** AMZN had entries sharing the same end date where one was a Q1 entry (~90d) and the other was a trailing 12-month entry (~365d). The B1 tiebreaker picked the longest duration (12-month), producing Q1 values that were the sum of 4 quarters instead of 1.

**What changed:** `getQuarterlyYTD` tiebreaker changed from "longest duration" to "closest to expected YTD duration" (Q1≈90d, Q2≈180d, Q3≈270d). Filed date remains as final tiebreaker.

**What worked:**
- AMZN: 67.3% → 78.2% (de-cumulation now uses correct Q1 values)
- Overall improvement modest because AMZN was the primary company affected

### B4: Date-Derived FY Matching — ABANDONED

**Status:** ❌ ABANDONED (caused 10pp+ regression)
**Attempted approach:** Add `fyEndMonth` parameter to all getter functions; use `getActualFY(endDate, fyEndMonth)` to compute correct FY from entry dates instead of trusting EDGAR's `fy` label.

**Why it failed:**
1. `extractFiscalYearEnds()` returns month abbreviation strings ('Sep','Mar') not numbers — initial implementation compared `month > 'Sep'` → NaN → broke all non-Dec FY companies
2. Even after fixing to numeric months: comparative entries from newer filings got reassigned to older FYs via date-derived matching, introducing extra entries that changed tiebreaker outcomes
3. January/February FY-end companies (LULU, ULTA, WSM) had catastrophic regressions (LULU 86.5% → 41.9%) because the boundary between FYs is fuzzy (some years end Jan 28, others Feb 4)
4. Overall dropped from 92.4% → 80.1%

**WMS investigation findings:** 50% of WMS's EDGAR 10-Q entries have wrong `fy` labels (confirmed via diagnostic). But WMS contributes only 217 DIFFs (6% of total). The global fix approach is too risky for the benefit.

**Conclusion:** WMS's fy mislabeling is real but a targeted fix would require a fundamentally different approach (e.g., pre-processing facts to remap fy labels for companies with detected mislabeling). Deprioritized in favor of higher-impact patterns.

## Conclusion

**Final quarterly accuracy: 92.8%** (up from 56.6% baseline)

The remaining 3,344 DIFFs are dominated by **structural differences** between XBRL taxonomy concepts and Morningstar's standardized financial data:
- **Residual/catch-all fields** (~725 DIFFs): accrued_liabilities, other_current/noncurrent_assets/liabilities — MS computes these by exclusion, XBRL reports directly with different component breakdowns
- **Financial sector** (~550 DIFFs): Banks, REITs, insurance companies use different revenue/investment/debt concepts
- **Lease accounting** (~120 DIFFs): ASC 842 tag availability gap
- **De-cumulation edge cases** (~200 DIFFs): Operating income, dividends, capex for non-Dec FY companies
- **Company-specific** (~370 DIFFs): WMS fy mislabeling, XYZ granular tag failures

These structural limitations are inherent to the XBRL-vs-Morningstar comparison and cannot be resolved without either:
1. Company-specific overrides (fragile, doesn't scale)
2. Fundamentally different extraction approach (e.g., parsing 10-Q HTML instead of XBRL)
3. Widening tolerances (gaming the metric)

**Recommendation:** Accept 92.8% as the practical ceiling for quarterly XBRL accuracy. Focus engineering effort on Phase 5+ (AI report generation) rather than diminishing returns on DIFF reduction.
