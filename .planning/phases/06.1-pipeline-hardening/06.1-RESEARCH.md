## Summary

Phase 06.1 addresses all 42 engineering issues identified in the COST Pitch Deck debrief. The COST run revealed that ~30% of wall-clock time was engineering overhead (file permission failures, DataPacket gaps, manual orchestration), and ~20% was orchestrator labor that should be automated. The DataPacket was only ~40% populated in Node.js because 6 engines depend on browser-only APIs (DOMParser, IndexedDB via `idb`, Vite middleware proxy routes) that `nodeAdapter.js` does not yet shim.

The fix strategy is well-defined: extend `nodeAdapter.js` to handle ALL browser-only APIs so engines run unmodified in Node.js, pre-process filings to markdown before agent dispatch, add `searchesPerformed` to agent output JSON with critic.js cross-checking, and build a generation status panel in the Pitch Deck UI. The existing infrastructure (`safeCall()` pattern in `dataExport.js`, `IS_NODE` detection in `nodeAdapter.js`, `PROXY_MAP` URL resolution, file-based cache, `progressState.js` state machine, `critic.js` quality checks) provides solid foundations for all five sub-phases.

**Primary recommendation:** Extend `nodeAdapter.js` with IndexedDB shim (redirect `idb` calls to file-based JSON), DOMParser shim (already exists but not wired to all engines), and direct HTTPS fetch for Vite middleware endpoints (Yahoo, Finviz, Alpha Vantage). This alone pushes the DataPacket from ~40% to 90%+ populated.

### Pattern 1: nodeAdapter.js Extension Strategy

**What:** Extend the existing Node.js adapter to shim remaining browser APIs without modifying any engine files.

**When to use:** For every engine that fails in Node.js due to browser-only APIs.

**How it works:**

The existing `nodeAdapter.js` already handles:
- `import.meta.env` -> `process.env` via dotenv
- DOMParser -> linkedom (via `createDOMParser()`)
- Proxy URL resolution (`PROXY_MAP`)
- File-based cache (`.thes1s/cache/`)

The extension needs to add:
1. **Global DOMParser injection** -- currently `createDOMParser()` exists but isn't injected globally. Engines like `insiders.js`, `compensation.js`, `finviz.js`, `filingMarkdown.js` use `new DOMParser()` directly.
2. **IndexedDB -> file-based cache redirect** -- `priceStore.js` uses `idb` (openDB). Need to intercept or replace with file-based storage for Node.js.
3. **Vite middleware bypass** -- `analystEstimates.js` fetches `/api/yahoo-summary/:ticker`, `batchQuotes.js` fetches `/api/yahoo-quotes/:tickers`, `finviz.js` fetches `/api/finviz/:ticker`. These Vite middleware routes run `yahoo-finance2` and `cheerio` server-side. In Node.js, call `yahoo-finance2` and `cheerio` directly.

**Critical architectural decision:** Do NOT modify engine files. The adapter pattern means engines work identically in browser and Node.js. The `assemble-data.js` script imports `nodeAdapter.js` first (side-effect import), which patches globals before engines load.

**Implementation approach:**
```javascript
// In nodeAdapter.js — add to existing file

// 1. Global DOMParser injection
if (IS_NODE) {
  globalThis.DOMParser = class {
    parseFromString(html, type) {
      const { document } = parseHTML(html);
      return document;
    }
  };
}

// 2. Monkey-patch idb module for Node.js
// The idb package wraps IndexedDB. In Node, intercept with file-based JSON.
// Approach: Create a fake-idb module that uses fs for storage.
// Alternative: Patch the cache.js module to detect IS_NODE and use file cache.

// 3. Vite middleware bypass
// For yahoo-finance2 endpoints, import the package directly.
// For finviz, use cheerio + fetch directly.
```

### Pattern 2: Filing Pre-Processing Pipeline

**What:** Convert SEC filings to markdown BEFORE dispatching PSR agents, injecting clean sections into agent prompts.

**Why:** PSR agents in the COST run fetched raw HTML via curl (100-200K+ tokens per filing). The app already has `filingMarkdown.js` which produces clean markdown. Pre-converting eliminates agent token waste and improves extraction quality.

**Architecture:**
```
DataPacket assembly
  -> filing list (accession numbers from EDGAR submissions API)
  -> for each 10-K: fetchFilingMarkdown() -> markdown
  -> section extraction (Item 1, Item 7, Risk Factors, etc.)
  -> inject relevant sections into PSR agent prompts
```

**Section extraction approach:**
SEC 10-K filings have standardized Item headers:
- Item 1: Business Description
- Item 1A: Risk Factors
- Item 7: MD&A
- Item 8: Financial Statements
Regex-based header detection on the markdown output, splitting at `## Item` boundaries.

### Pattern 3: searchesPerformed Self-Report + Audit

**What:** Two-layer verification that agents actually perform mandated web searches.

**Layer 1 (Self-Report):** Each agent includes a `searchesPerformed` array in its JSON output:

**Layer 2 (Audit):** `critic.js` cross-checks:
1. Are there web-sourced citations in the section?
2. Do the `searchesPerformed` queries align with curriculum-mandated searches?
3. Flag sections with zero web citations as `severity: high`.

### Anti-Patterns to Avoid

- **Modifying engine files for Node.js compatibility:** Engines must work identically in browser and Node.js. All adaptation goes through `nodeAdapter.js`.
- **Having agents fetch filings at runtime:** Pre-process filings. Agent token budgets should go to analysis, not HTTP fetching.
- **Trusting agent self-report alone for search verification:** Always pair with audit. Agents may claim searches they did not perform.
- **Blocking generation on quality failures:** Quality checks are informational (per existing D-04 decision). Report saves first, quality runs after.
- **Building aiResearch.js in this phase:** Explicitly deferred. CC pipeline optimization only.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Yahoo Finance data in Node.js | Custom HTTP + cookie handling | `yahoo-finance2` package (already a dependency) | Cookie/crumb auth is complex and changes frequently |
| DOM parsing in Node.js | Custom HTML parser | `linkedom` (already a dependency) + `cheerio` (already a dependency) | Battle-tested, handles malformed EDGAR HTML |
| Filing markdown conversion | New converter for Node.js | Existing `filingMarkdown.js` with DOMParser shim | Already handles EDGAR tables, iXBRL stripping, 244 lines of tested code |
| IndexedDB in Node.js | Full IndexedDB polyfill | File-based JSON cache (existing `nodeAdapter.js` pattern) | Only 2 stores used: `thes1s-prices` and `thes1s-cache`. File-based is simpler. |
| Progress polling | WebSocket server | File polling via `/api/thes1s/` Vite middleware | No-server architecture constraint. File polling is sufficient for 2-second updates. |

**Key insight:** Almost every dependency needed for Node.js compatibility is already in `package.json` (`yahoo-finance2`, `cheerio`, `linkedom`, `idb`). The problem is not missing libraries but missing wiring between the Node.js adapter and the engines.

## Common Pitfalls

### Pitfall 1: IndexedDB Shim Complexity

**What goes wrong:** Attempting to polyfill the full IndexedDB API for Node.js leads to a rabbit hole of transaction semantics, cursor behavior, and version upgrade handling.

**Why it happens:** The `idb` package is a thin wrapper over IndexedDB. Shimming IndexedDB itself is complex.

**How to avoid:** Do NOT polyfill IndexedDB. Instead, intercept at the `cache.js` layer. The `cache.js` module already has `isIDBKey()` routing -- when `IS_NODE` is true, redirect ALL cache operations (including IDB-prefixed keys) to the file-based cache. The `priceStore.js` module (which uses `idb` directly for prices) needs a separate file-based implementation for Node.js.

**Warning signs:** If you find yourself implementing `IDBTransaction`, `IDBCursor`, or `IDBObjectStore`, you have gone too far.

### Pitfall 2: Vite Middleware Endpoint Mismatch

**What goes wrong:** The Node.js adapter resolves proxy URLs (`/api/sec/` -> `https://www.sec.gov/`) but does NOT handle Vite middleware routes that run server-side JavaScript (yahoo-finance2 calls, cheerio HTML parsing).

**Why it happens:** `PROXY_MAP` handles simple URL rewriting. But `/api/yahoo-summary/:ticker` is not a proxy -- it is a Vite middleware plugin that calls `yahoo-finance2.quoteSummary()` server-side. Similarly, `/api/finviz/:ticker` scrapes Finviz HTML server-side with cheerio.

**How to avoid:** For each Vite middleware endpoint, create a Node.js equivalent function that calls the underlying library directly:
- `/api/yahoo-summary/:ticker` -> `yahoo-finance2.quoteSummary(ticker, { modules: [...] })`
- `/api/yahoo-quotes/:tickers` -> `yahoo-finance2.quote(tickers.split(','))`
- `/api/finviz/:ticker` -> `fetch(finvizUrl) + cheerio.load(html)`

**Warning signs:** If engines get `ECONNREFUSED` on `localhost:5173`, they are trying to reach a Vite middleware endpoint that does not exist in Node.js.

### Pitfall 3: Filing Section Extraction Regex Fragility

**What goes wrong:** SEC filing section boundaries vary wildly. Some use `<h2>Item 1.`, others use `ITEM 1.`, others use inline bold text. Regex-based splitting breaks on non-standard filings.

**Why it happens:** There is no mandatory HTML structure for SEC filings. Companies use different formatting, and even the same company may change format across years.

**How to avoid:** Use the markdown output from `filingMarkdown.js` (which normalizes HTML to consistent heading levels), then split on normalized `## Item` or `# Item` patterns. Accept that some filings will not split cleanly -- return the full markdown as a single section rather than failing.

**Warning signs:** If section extraction returns empty strings or tiny fragments for some filings, the regex is too strict.

### Pitfall 4: Agent File Write Permissions in CC

**What goes wrong:** CC subagents use the Write tool to save section JSON. The Write tool may be denied by the IDE permission system, causing the agent to hang or fail.

**Why it happens:** The IDE may require explicit user approval for file writes to certain paths.

**How to avoid:** Two fallback strategies:
1. Have agents write via the Bash tool (`cat << 'EOF' > path`) instead of Write tool
2. Have agents return JSON in their response text, and the orchestrator (parent CC session) extracts and saves it

The second approach is more reliable because it does not depend on file system permissions at all.

**Warning signs:** Agent output contains `"Write tool denied"` or agent hangs after completing analysis.

### Pitfall 5: searchesPerformed Hallucination

**What goes wrong:** Agents include a `searchesPerformed` array but fabricate search queries they never actually executed, or report `resultCount: 0` for searches they claim to have done.

**Why it happens:** LLMs can confabulate tool usage when prompted to self-report.

**How to avoid:** The audit layer in `critic.js` must check for EVIDENCE of searches, not just self-report:
1. Does the section have web-sourced citations? (Type = `web_url`)
2. Do citation URLs correspond to search topics in `searchesPerformed`?
3. Flag sections with `searchesPerformed.length > 0` but zero web citations as suspicious.

**Warning signs:** High `searchesPerformed` count with zero or few `web_url` type citations.

## Open Questions

1. **IndexedDB shim strategy -- cache.js interception vs idb polyfill**
   - What we know: `cache.js` has key routing (`isIDBKey()`). `priceStore.js` uses `idb` directly.
   - What's unclear: Whether intercepting at `cache.js` is sufficient or if `priceStore.js` needs its own file-based implementation.
   - Recommendation: Intercept at `cache.js` (covers most engines) + create `filePriceStore.js` for prices specifically. Two small changes vs one large polyfill.

2. **Filing section header detection robustness**
   - What we know: SEC filings have standardized Item numbers but inconsistent formatting.
   - What's unclear: How many filing formats exist across the universe (not just COST).
   - Recommendation: Start with regex on markdown output (`/^#{1,3}\s*Item\s+\d/im`), fall back to returning full markdown. Test against 5-10 tickers in verification.

3. **generation-status.json delivery to React component**
   - What we know: `usePitchDeck.js` polls `/api/thes1s/reports/{TICKER}/progress` every 2 seconds.
   - What's unclear: Whether existing Vite middleware serves `.thes1s/` files or if a new route is needed.
   - Recommendation: Add a Vite middleware route that reads `generation-status.json` from disk and serves it as JSON. Minimal code.

4. **COST balance sheet field gaps**
   - What we know: `total_assets`, `total_equity`, `cash_and_equivalents`, `shares_diluted` are undefined in COST DataPacket.
   - What's unclear: Whether this is a nodeAdapter issue (some cache not loading) or a genuine XBRL extraction gap for COST.
   - Recommendation: Debug by running `fetchEdgarStatements('COST')` in Node.js with full logging. The XBRL engine has 96.1% coverage on S&P 500 -- COST is S&P 500, so these fields should resolve.
