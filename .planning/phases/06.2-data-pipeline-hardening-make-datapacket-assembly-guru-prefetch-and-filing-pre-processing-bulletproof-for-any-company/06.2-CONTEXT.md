# Phase 6.2: Data Pipeline Hardening - Context

**Gathered:** 2026-03-26
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 6.2 makes the data pipeline bulletproof for any company. DataPacket assembly, guru prefetch, and filing pre-processing must produce complete, accurate data every time — or clearly report what's missing so the PM can fill gaps manually. This is foundational infrastructure that every downstream agent depends on.

**Key constraint:** This is a fix-and-harden phase, not a redesign. We extend existing engines (`dataExport.js`, `gurus.js`, `filingSections.js`, `preprocess-filings.js`, `prefetch-gurus.js`) and add a new pipeline checkpoint. No new agents or UI components.

</domain>

<decisions>
## Implementation Decisions

### Filing Section Extraction — 10-Ks
- **D-01:** Extract 4 sections from each 10-K: **Business (Item 1), Risk Factors (Item 1A), MD&A (Item 7), Financial Statements (Item 8)**. Financial Statements includes footnotes (Notes to Consolidated Financial Statements) where companies disclose acquisitions, segment breakdowns, lease obligations, and accounting policy changes.
- **D-02:** Pre-process **5 years** of 10-Ks (up from current 3). Covers a full business cycle. Room to add a second PSR agent for years 6-10 in a future phase.

### Filing Section Extraction — 10-Qs
- **D-03:** Extract 3 sections from each 10-Q: **MD&A (Item 2), Financial Statements (Item 1), Risk Factors (Item 1A)**. Note: 10-Q item numbers differ from 10-K — this is the root cause of the current extraction failure (SECTION_MAP is hardcoded for 10-K numbers).
- **D-04:** Pre-process **8 quarters** of 10-Qs (up from current 4). Two full fiscal years of quarterly data enables meaningful promise tracking and trend analysis.

### Form-Aware Section Extraction
- **D-05:** `filingSections.js` must be form-aware. Either accept a `formType` parameter with separate SECTION_MAPs for 10-K vs 10-Q, or use patterns that match both numbering schemes. The current single SECTION_MAP with 10-K item numbers is the root cause of 10-Q extraction failures.

### PSR Cross-Validation Flow
- **D-06:** The annual-reader cross-validates financial data from 10-K Financial Statements (including footnotes) against the DataPacket. SEC filing is always source of truth. If the PSR finds discrepancies (XBRL normalization errors, accounting changes, restatements), it elevates to the orchestrator, who records the corrected values. Those corrections flow to all downstream agents (financial-analyst, valuation-specialist, etc.) via the `psrFindings` object. This is already designed in Phase 6 (D-10, D-11) — Phase 6.2 ensures the filing data is actually extracted so cross-validation can happen.

### Guru Prefetch Fix
- **D-07:** The prefetch script (`prefetch-gurus.js`) must add ticker resolution after fetching portfolios. The root cause: `fetchAllGuruHoldings()` returns raw 13F data with CUSIP identifiers but no ticker symbols. The app's Gurus tab has a self-heal step (`resolveTickersForHoldings()`) that maps CUSIPs to tickers — the prefetch script needs the same logic.

### DataPacket Reliability — 25/25 Fields
- **D-08:** The `analystEstimates` field (currently the 25th missing field) must have a **fallback chain**: try Yahoo Finance first, retry once on timeout, fall back to Finviz scraping, then mark as unavailable. Same pattern for any field with multiple possible sources.
- **D-09:** **Fallback chains + 1 retry** as the standard reliability pattern. For each data source: try primary, retry once after 5-10 seconds on timeout, then try fallback source if available. Mark as unavailable only after exhausting all options. Fast and resilient.

### DataPacket Speed
- **D-10:** Investigate and optimize DataPacket assembly time (currently 30-60s). Parallelization of independent API calls, caching improvements, and timeout optimization. Specific approach is Claude's discretion.

### Data Quality Checkpoint
- **D-11:** New pipeline step between data assembly/pre-processing and agent dispatch. Prints a **summary table** showing all 25 DataPacket fields (populated/missing), filing extraction results (sections per filing per year), and guru results. **Blocks dispatch** if critical fields are missing (financials, filings, company info). **Warns but continues** on non-critical gaps (analyst estimates, transcripts, guru data).
- **D-12:** PM can **paste text** and **attach files** at the checkpoint to fill gaps. Example: if filing pre-processing fails for a specific 10-K, the PM can download the filing markdown from Thes1s's filing viewer and attach it directly into the chat. The orchestrator includes attached content in agent context.
- **D-13:** **Transparent degradation** for companies with genuinely unavailable data. Pipeline runs what it can, clearly marks what's missing and why. PM sees the full picture at checkpoint and decides whether to proceed, attach data manually, or abort. No silent gaps.

### Claude's Discretion
- DataPacket parallelization strategy (which API calls can run concurrently)
- Exact retry timing and backoff intervals
- SECTION_MAP implementation approach (separate maps vs. dual-pattern regexes)
- Checkpoint table formatting and layout
- How attached files are parsed and injected into agent context
- `preprocess-filings.js` internal refactoring to support form-aware extraction and increased depth
- nodeAdapter.js extensions needed for any new fallback sources

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `resolveTickersForHoldings()` in `gurus.js` — Already maps CUSIP→ticker via cache + issuer name matching. Just needs to be called from the prefetch script.
- `fetchFilingMarkdown()` in `filingMarkdown.js` — HTML→markdown conversion already works. Node.js compatible via nodeAdapter.
- `extractAllSections()` in `filingSections.js` — Section extraction works for 10-Ks. Needs form-awareness, not a rewrite.
- `fetchAnalystEstimates()` in `analystEstimates.js` — Primary source. Finviz scraping already exists in `finviz.js` as potential fallback.

### Established Patterns
- `nodeAdapter.js` shims browser APIs for Node.js — extend for any new needs, don't modify engines directly
- Error handling pattern: try/catch → return null → caller checks for null. Consistent across all engines.
- Cache pattern: check memory → check IndexedDB/localStorage → fetch from API → cache result

### Integration Points
- `preprocess-filings.js` calls `fetchFilingMarkdown()` then `extractAllSections()` — the form-type parameter needs to flow through this chain
- `assemble-data.js` calls `dataExport.js` which orchestrates all API fetches — parallelization happens here
- `SKILL.md` Step 2 → Step 2.1 → Step 2.5 is the data assembly pipeline — checkpoint inserts after Step 2.5

</code_context>

<specifics>
## Specific Ideas

- PM should be able to download a filing from Thes1s's markdown viewer and attach it directly when pre-processing fails — "adds one extra step but ensures depth"
- PSR findings must flow to ALL downstream agents, not just the financial-analyst. Rule One research always builds on itself — a risk factor found in footnotes affects the business-analyst and risk-analyst too.
- Start with 5 years of 10-Ks now; add a second PSR agent for years 6-10 later. One step at a time.

</specifics>
